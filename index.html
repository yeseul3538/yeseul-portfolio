운영 기획

  • 반복 이슈 분석 → 표준 프로세스 설계
  • SOP·플레이북·사용자 가이드 문서화
  • 데이터 정합성 확보 (매칭·검증 프로세스)

분기 로직 명세

복잡한 비즈니스 조건을 분기 명세로 옮기고, UI와 기초 데이터를 포함해 개발자가 구현 가능한 형태로 전환합니다.

  • 비즈니스 조건의 분기 명세화
  • 개발 명세서 작성
  • 엣지 케이스 도출·QA 테스트 설계

부서 간 협업

각 부서의 입장과 우선순위를 이해하고, 서로 다른 요구사항을 하나의 기준으로 정리해 합의를 이끌어냅니다.

  • 유관 부서 요구사항 조율
  • R&R 분장표 기반 책임 분리

프로젝트 01

미납 가맹점 관리 체계 구축

출금 정책 재설계부터 단계별 회수·추심 이관까지

결제 운영2024–2026정책 기획프로세스 설계
  • 미납금 평균 회수율 8% → 15% (가맹점 증가로 미납 규모가 커지는 중에도 개선)
  • 최근 1년 월평균 회수액 약 250만 원, 최대 월 700만 원
  • 일괄 출금 → 부분 출금 정책 전환, 수수료 역전 구간 사전 차단
정책 기획Outbound 설계Apps Script
자세히 보기

문제 정의

  • CMS 미납 가맹점을 관리하는 체계가 없어, 미납 데이터부터 새로 만들어야 했습니다.
  • 잔액이 총 미납금 이상일 때만 일괄 출금하는 CMS 방식 때문에, 잔액이 부족한 가맹점의 미납이 회수 없이 계속 쌓였습니다.
  • 전월 미납 고객에 대한 사후 대응에 그쳐 장기·고액 미납이 누적되었고, 폐업 후 연락 두절 같은 회수 사각지대도 있었습니다.

목표

  • 사후 대응에 그치던 미납 관리를, 출금 정책부터 회수·추심까지 이어지는 단계별 체계로 바꾸기

내 역할

  • 출금 정책 AS-IS 분석, 변경안 도출 및 적용
  • 미납 데이터 최초 구축, 분류 기준과 4단계 Outbound 설계
  • 국세청 휴·폐업 자동 조회 Apps Script 제작
  • CX·Finance와 추심 이관 프로세스 수립, 주간 현황 보고

진행 과정

  1. 정책 진단

    잔액이 총 미납금 이상일 때만 출금하는 방식 때문에 저잔액 가맹점의 미납이 회수 없이 쌓이는 구조 확인

  2. 정책 변경과 리스크 검증

    부분 출금 전환 전, 잔액 200원 미만에서 출금액보다 이체 수수료가 커지는 역전 구간 발견 → 최소 출금 단위로 차단. 월 CMS 1천 원 미만 소액 가맹점은 금액대별로 분석해 의사결정 근거 마련

  3. 감지와 분류

    미납 데이터 신규 구축, 최근 기준 월 약 2,300만 원 규모의 미납을 장기·고액·일반으로 분류. 국세청 휴·폐업 자동 조회(30분 주기)로 폐업 가맹점 우선 선별

  4. 단계별 회수

    자동이체 출금일에 맞춘 5일 → 10일 → 14일 → 20일 4단계 Outbound 설계. 6개월 미입금 시 외부 추심사 이관 기준 수립, CX팀 응대 매뉴얼 전달, Finance팀과 수수료·세금계산서 처리 기준 정합

  5. 주간 보고

    매주 팀 위클리 미팅에 미납·회수 현황 보고 → 리더 미팅의 의사결정 자료로 활용

결과·산출물

  • 미납금 평균 회수율 8% → 15% (회수율 = 월 회수액 ÷ 월 총 미납금)
  • 최근 1년 월평균 회수액 약 250만 원, 최대 월 700만 원
  • 정책 적용 후 미납 비율(금액 기준) 약 30% → 27%
  • 부분 출금 정책 실제 적용, 수수료 역전 구간 차단
  • 6개월 미입금 시 추심사 이관 로직 표준화

배운 점

  • 좋은 정책 가설도 엣지 케이스 하나로 손해가 될 수 있어, 수치로 먼저 검증해야 했습니다.
  • 데이터가 없을 때는 기준부터 만들어야 했고, 분류가 명확해야 다음 액션도 명확해졌습니다.
프로젝트 02

가맹점 라이프사이클 관리

해지·폐업 트래킹 프로세스 구축

운영 기획2025프로세스 설계
  • 해지 위약금 월 순회수액 40만 원 → 160만 원 (4배, 환불 차감 후)
  • 폐업 조기 감지로 월 청구 건수 15건 → 90건
  • 위약금을 장비 반납 유도 장치로 재설계 (반납 시 환불, 미반납 시 실제 장비 손실 기준 청구)
크로스 검증Slack 자동화
자세히 보기

문제 정의

  • 해지·폐업 가맹점 트래킹이 부재해 CMS·위약금 입금 누락이 반복되었습니다.
  • 국세청상 사업자가 정상 운영 중이고 단말기 사용도 확인되는데 전산상 해지 처리된 케이스가 방치되어 금전적 손해와 데이터 불일치가 발생했습니다.

목표

  • 해지·폐업 가맹점을 조기에 감지해 CMS·위약금 입금 누락을 막고, 전산 상태를 실제 운영 상태와 일치시키기
  • 해지 위약금을 실제 장비 손실에 맞게 산정하기

내 역할

  • 단독 진행 — 감지 → 데이터 크로스 검증 → 프로세스 설계 → Slack 자동화 구축까지 전 과정

진행 과정

  1. 감지

    CX 상담 내역 중 해지 / 폐업 문의 매일 확인, 가맹점 사업자번호 휴·폐업 조회

  2. 진단

    장비 회수 데이터 + 국세청 + CX 상담 내역 크로스 검증, 문제 건수·유형별 케이스 정량 파악

  3. 위약금 구조 재설계

    "월 CMS × 잔여 개월 수" 방식은 장비 36개월 정상 사용을 전제로 한 요금이라 중도 해지 시 실제 장비 손실 미반영 → 해지 시점 감가상각 잔존가치 기준으로 재설계. 장비 정상 반납 시 위약금을 환불해 손실 보전과 장비 회수 유도를 함께 설계

  4. 데이터 자동 적재

    고객 여정 시작부터 끝까지 퍼널별 데이터가 한 번의 입력으로 자동 적재되는 프로세스 구축

  5. 후속 처리 표준화

    Slack 자동화 + 담당자 지정 + 후속 작업 표준화로 재발 방지

결과·산출물

  • 해지 위약금 월 순회수액 40만 원 → 160만 원 (장비 반납 건 환불 차감 후)
  • 고객 문의를 기다리던 방식에서 폐업을 먼저 감지해 연락하는 방식으로 전환 → 월 청구 건수 15건 → 90건
  • 위약금 산정을 실제 장비 손실 기준으로 변경 (대표 사례 건당 18만 원 → 48만 원)
  • 지속 미납 건은 추심사로 이관하고, 청구 기준 변경에 맞춰 계약서 상세 약관을 개정해 분쟁 근거 정비
  • 퍼널별 데이터 자동 적재, 가맹점 안내·진행 프로세스 표준화

배운 점

  • 한 가지 데이터만으로는 상태를 판단할 수 없고, 여러 출처를 교차해야 실제 문제가 보였습니다.
프로젝트 03

영업 리드 추적 자동화 및 성과 리포트 구축

인입 경로 수동 매칭 → GAS·Slack 자동 분류

운영 기획2026업무 자동화
  • 영업 리드 인입 경로 95% 자동 분류 (수동 매칭 5% 미만 유지)
  • 수동 매칭 시간 하루 2시간 → 20분
  • 주간 성과 리포트 자동 집계 → 대표 보고·KPI 측정에 활용
Apps ScriptSlack 연동데이터 관리
자세히 보기

문제 정의

  • 일 평균 200건 이상 인입되는 영업 리드의 경로를 수동으로 매칭하느라 하루 2시간이 소요되었습니다.
  • 채널·담당자별 데이터가 파편화되어 영업 전환율과 성과를 추적할 수 없었습니다.

목표

  • 영업 리드 인입 경로를 자동으로 분류해 수동 매칭 리소스 줄이기
  • 채널·담당자별 성과를 주 단위로 추적할 수 있는 리포트 구조 만들기

내 역할

  • 영업 리드 운영 구조 설계·예외 상황 기준 정리
  • Google Apps Script·Slack 연동 자동화 개발
  • 주간 성과 리포트 구조 구축 (보고는 파트장이 진행)

진행 과정

  1. 사용자 동선 확인

    운영 흐름을 분석해 영업 리드 추적 및 담당자별 실적 측정 구조 정리

  2. 예외 케이스 정리

    담당자 변경·중복 등 예외 상황 기준을 정립하고 분류 기준 및 시나리오 설계

  3. 인입 채널 단일화

    파편화된 인입 채널 데이터를 표준화하고 실무자 사용 동선 단순화·가이드 배포

  4. GAS 자동화 구축

    Google Apps Script와 Slack 연동으로 실시간 리드 분류 시스템 개발

  5. 성과 리포트

    단순 문의와 실제 전환 리드를 구분해 주간 성과 리포트가 자동 집계되는 구조 확립

결과·산출물

  • 영업 리드 인입 경로 95% 자동 분류 (수동 매칭 5% 미만 유지)
  • 수동 매칭 시간 하루 2시간 → 20분
  • 주간 성과 리포트를 매주 대표 보고와 KPI 측정에 활용

배운 점

  • 자동화보다 먼저 예외 상황의 기준을 정해야 분류 결과를 믿고 쓸 수 있었습니다.
  • 데이터를 한곳으로 모으자 성과를 측정하고 보고하는 구조까지 이어졌습니다.

법인카드 재발급 일괄 처리

건별 수기 재발급 → Excel 업로드 일괄 처리 전환

운영 기획2023프로세스 설계
  • 기업 1곳 재발급 처리 시간 4–6시간 → 15분 (최대 96% 단축)
  • 1–2주마다 반복되던 담당자 1명 전담 업무를 해소해 팀 리소스 확보
  • 카드 정보 다운로드 → 수정 → 일괄 업로드로 재발급 흐름 표준화
업무 자동화개발 협업프로세스 설계

문제 정의

  • 법인카드는 최초 가입 시 전 직원 카드를 일괄 발행하는 경우가 많아, 5년마다 유효기간이 만료되면 기업 단위로 전 직원 카드를 한꺼번에 재발급해야 했습니다.
  • 일괄 재발급 시스템이 없어 재발급 시즌마다 직원 1명이 다른 업무에서 빠져 카드를 한 장씩 수기로 처리했습니다 (기업 1곳당 4–6시간).
  • 법인카드 사용률 국내 2위로 담당 기업이 많아 이 업무가 1–2주에 한 번꼴로 발생했고, 인력 공백과 수작업 피로가 누적되었습니다.

목표

  • 기업 단위 재발급을 한 번에 처리해, 반복되던 전담 인력 투입을 없애기

내 역할

  • 반복 주기·소요 시간·투입 인력 기준으로 병목 진단
  • 다운로드 → 수정 → 업로드 흐름 정의, 개발팀과 요구사항 협의·운영 적용

진행 과정

  1. 진단

    반복 주기·소요 시간·투입 인력을 기준으로 건별 수기 처리의 병목 정의

  2. 흐름 설계

    기존 카드 정보 Excel 다운로드 → 정보 유지 또는 일부 변경 → 시스템 업로드로 이어지는 재발급 흐름 정의

  3. 개발 협업

    개발팀에 요구사항을 전달해 Excel 업로드 기반 일괄 재발급 기능 구현

  4. 적용

    기업 단위 재발급을 업로드 한 번으로 처리하도록 운영 방식 전환

결과·산출물

  • 기업 1곳 재발급 처리 시간 4–6시간 → 15분
  • 1–2주 주기로 발생하던 전담 인력 투입 해소 → 상담·운영 업무에 리소스 재배치
  • 카드 한 장씩 반복하던 수기 입력 업무 제거 → 작업 피로도 해소

배운 점

  • 비용을 주기 × 시간 × 인력으로 수치화하니 개선의 필요성을 설득하기 쉬웠습니다.
  • 실무자가 이미 쓰는 도구(Excel)의 흐름에 맞추니 도입이 수월했습니다.

분기 명세개발 협업QA

문제 정의

  • 고객 측 계약 해지 시 위약금 부과가 진행되어야 하나 계약서 버전별로 위약금 산정식에 차이가 있었습니다.
  • 계약서 디벨롭을 진행하며 우선 Google Sheet 계산기를 만들어 배포하였습니다.
  • 늘어나는 CX 문의와 다양해지는 계약 내용으로 Google Sheet 수기 진행에 병목이 발생하였습니다.

목표

  • 계약서 버전별로 다른 산정식을 하나의 툴로 통합해, 누가 계산해도 같은 결과가 나오게 하기

내 역할

  • QA (보완 요구사항 11건 도출)·사용자 가이드 작성·CX 온보딩
  • 개발은 개발팀이 담당

진행 과정

  1. 계약내용 분해

    3-Step UI (계약유형 → 메인 → 추가장비)로 분기 명세화

  2. 개발 명세서 작성

    4가지 조건별 산정식·부가세 처리 분기를 명세서로 정리해 개발자에게 전달

  3. QA

    1차 빌드 검증 → 11건 보완 요구사항 도출 (미설치 케이스 / 설치비 추가 청구 등)

  4. 배포

    사용자 가이드 작성 + 사내 공지 + CX팀 온보딩

결과·산출물

  • 4가지 계약 유형 통합 (오프라인·온라인 초회·온라인 갱신·케어서비스)
  • 11건 QA 보완 요구사항 도출 및 반영
  • 부가세 처리 분기 표준화·사용자 가이드 작성·사내 배포 완료

  • 조건을 개발자가 구현할 수 있는 수준까지 쪼개는 것이 기획의 핵심이었습니다.
  • 엣지 케이스는 실제 빌드를 검증하면서 드러났습니다.
프로젝트 06

대량 발급 오류 사전 표기

현업의 불편을 개발 가능한 요구사항으로 전환

운영 기획2023개발 요구사항 정의
  • 오류 건 처리 시간 건당 30분–1시간 → 10–20분
  • 기존 화면·단계를 유지하는 대안으로 개발 우선순위가 낮던 요청 반영
요구사항 정의개발 협업리드타임 분석
자세히 보기

문제 정의

  • 법인카드 대량 발급 도중에는 오류를 확인할 수 없어, 최종 단계에서야 오류 건을 걸러냈습니다.
  • 걸러진 오류 건은 예외로 빼 두었다가 수기로 다시 발급해야 했고, 건당 30분–1시간이 걸렸습니다.
  • 법인카드 시스템은 개인카드 시스템보다 개발 우선순위가 낮아 개선 요청이 반영되기 어려웠습니다.

목표

  • 오류를 최종 단계가 아니라 발급 처리 도중에 확인할 수 있게 하기

내 역할

  • 현업 요청을 핵심 요구·제약·대안으로 나눠 정리
  • 오류 건 수기 재발급 리드타임을 정리해 개발 필요성의 근거로 제시
  • 개발 부담이 적은 대안 방식 제안

진행 과정

  1. 핵심 요구

    오류를 최종 단계가 아니라 처리 도중에 확인해야 한다는 요구로 정리

  2. 근거 정리

    개발 우선순위가 낮은 제약을 넘기 위해 오류 건 수기 재발급에 드는 리드타임(건당 30분–1시간)을 정리해 제시

  3. 대안 제안

    기존 화면과 단계는 그대로 두고, 발급 정보에 조건값을 걸어 조건에 맞지 않는 데이터를 바로 표기하는 방식 제안

  4. 반영

    화면을 바꾸지 않아 개발 부담이 적은 방식으로 제안 반영

결과·산출물

  • 발급 처리 도중 오류 건을 바로 확인
  • 오류 건 처리 시간 건당 30분–1시간 → 10–20분

배운 점

  • 현업의 불편을 개발팀이 판단할 수 있는 요구사항으로 바꾸는 것이 협업의 출발점이었습니다.
  • 우선순위가 낮은 요청일수록 리드타임 같은 근거와 개발 부담이 적은 대안을 함께 제시해야 반영되었습니다.

R&RZapier워크플로우

문제 정의

  • 장비 출고·계약서·회계 데이터가 각각 다른 팀에서 관리되어 정합성이 무너지고, 백업 부재로 오출고·계약서 미수취 등이 발생하였습니다.
  • 임대장비는 회사 귀속 자산이므로 누락된 데이터로 인해 회계 감사 시에도 문제가 생길 수 있는 상황이었습니다.

목표

  • 출고·계약서·회계 데이터를 하나의 기준으로 맞추고, 오출고와 감사 리스크를 미리 차단하기

내 역할

  • 문제 진단, 출고 워크플로우·자동 적재·48시간 알림(Zapier) 설계
  • R&R로 부서별 책임 정리, SCM·Finance·Commerce 협업 조율

진행 과정

  1. 진단

    출고 요청 데이터 미적재로 인한 오출고·이중 출고, 커머스팀 임의 처리로 인한 데이터 오류 확인

  2. 표준화

    출고 요청 표준 워크플로우 전환, 48시간 내 미확인 시 담당자 자동 메일·Slack 알림 (Zapier). R&R 분장표로 출고부터 회수까지 담당 부서 정리

  3. 정기 점검

    월간 출고 ↔ 계약서 크로스체크로 계약서 미수취·오출고·미회수 건을 담당자에게 전달

결과·산출물

  • 출고 요청 워크플로우 도입 + 스프레드시트 자동 적재 시스템 구축
  • SCM·Finance·Commerce 팀 협업 프로세스 설계
  • 월간 출고 ↔ 계약서 크로스체크 도입

배운 점

  • 여러 팀이 같은 데이터를 다룰 때는 도구보다 책임 소재를 먼저 정해야 했습니다.
